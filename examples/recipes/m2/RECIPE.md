# Local-81 RECIPE — onboard an M2 stack fleet (JBoss / Oracle / PostgreSQL / MQ)

**What this is:** a thin, read-only front-end that classifies any host with `m2`
in its name, discovers *where its stack lives* (paths, services, packages, config),
and projects the fleet into a validated `local81.recipes.v1` catalog. You are not
bypassing anything — it feeds the real `doctor` / `pull-logs` / `deploy` tools.

## The naming convention

Hosts are classified by the first marker substring in their name:

| Name contains | Role          | Stack the discovery probes look for |
|---------------|---------------|--------------------------------------|
| `m2in`        | `m2-postgres` | PostgreSQL 17 server/service/data/config |
| `m2or`        | `m2-oracle`   | `/etc/oratab`, `ORACLE_HOME`, listener/tnsnames, `ora_pmon` instances |
| `m2tr`        | `m2-mq`       | IBM MQ `/opt/mqm` + `/var/mqm`, `dspmq`, `qm.ini`, `*.mqsc` |
| `m2` (other)  | `m2-app`      | Apache `/var/www/html/vhosts`, JBoss `$JBOSS_HOME/standalone/`, `/props`, the Java client under `/app`, `engin/palmed`, `smartxfr` |

Every role also probes the **shared base**: the Java client root `/app` and the
Oracle client root `/opt` (with a `tnsnames.ora` sweep). A name with no `m2`
marker is a **hard error** (fail-closed) — a typo can't silently onboard the
wrong box.

## 1. List your hosts

One host per line (`#` comments and blanks ignored) — see [`hosts.example.txt`](hosts.example.txt):

```
a70lspalm2ex001
a70lspalm2in001
a70lspalm2or001
a70lspalm2tr001
```

## 2. Classify (read-only, contacts nothing)

```bash
local81 m2 classify --hosts-file hosts.example.txt
# a70lspalm2ex001 -> m2-app
# a70lspalm2in001 -> m2-postgres
# a70lspalm2or001 -> m2-oracle
# a70lspalm2tr001 -> m2-mq
```

## 3. Plan the discovery + render the fleet catalog

```bash
local81 m2 plan --hosts-file hosts.example.txt --out m2-out
```

Writes into `m2-out/`:

| file | what it's for |
|---|---|
| `fleet-m2.yaml` | a validated `local81.recipes.v1` catalog (hosts grouped by role) — drives `ui semaphore-render` / `ui n8n-render` / `deploy` |
| `discover/<host>.sh` | a **read-only** bash report for that host (stat/test/systemctl/find only — never writes) |
| `discovery-plan.tsv` | every host × check × kind × target, greppable |

`--format json` emits the whole plan (including the exact probe argv) for an
n8n node, a CI step, or the bundled MCP server. A ready-made example catalog is
checked in at [`fleet-m2.yaml`](fleet-m2.yaml).

## 4. Run the discovery on a host (still read-only)

```bash
ssh a70lspalm2in001 'bash -s' < m2-out/discover/a70lspalm2in001.sh
```

Every line only observes — it stats paths, queries `systemctl`/`dpkg`/`rpm`, and
`find`s `.xml`/`.properties` config. Nothing is installed, started, or written.

## 5. Wire into the rest of Local-81

```bash
local81 doctor --fleet                                  # reachable + carries the 5 POSIX tools
local81 ui semaphore-render --catalog m2-out/fleet-m2.yaml --db-host <pg>
local81 pull-logs --hosts a70lspalm2ex001 \
  --jboss-path '$JBOSS_HOME/standalone/log' \
  --engin-path /app/engin/palmed/logs \
  --smartxfr-path /app/smartxfr/logs        # pull-logs already understands this stack
```

Before using the deploy/build matrix, set each recipe's placeholder `port:` in
`fleet-m2.yaml` to the host's real service port.

## Why this is the right way

- **Read-only by construction** — classification and discovery never mutate a
  target or contact the network beyond the SSH you run yourself.
- **Fail-closed** — a non-`m2` name is an error, not a silent guess.
- **One source of truth** — the catalog the whole control plane re-renders from,
  generated by the same code path the tests exercise.
- **Honest about the stack** — it reports where JBoss/Oracle/PostgreSQL/MQ config
  *is*, and labels what's absent, instead of pretending.
