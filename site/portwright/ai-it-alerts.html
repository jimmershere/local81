Agentjacking: log injection turns your AI agent into the attacker's hands

Filed 2026-06-22 · Source: security researchers reported this technique publicly; details paraphrased.

Security researchers have described an attack pattern they call "Agentjacking" — a form of indirect prompt injection that targets AI coding agents such as Claude Code, Cursor, and similar tools.

How it works, in plain language

  1. An attacker plants malicious instructions disguised as ordinary data — for example, by submitting a crafted error to a publicly reachable telemetry endpoint (a leaked or public Sentry DSN is one reported avenue). The poisoned text now lives in your logs or error reports alongside legitimate entries.
  2. Later, a developer asks their AI agent something innocent like "look into these errors for me." The agent pulls the logs — often through an MCP server or an API — and reads the attacker's text as part of its context.
  3. Because today's LLMs do not reliably separate data from instructions, the agent can treat the injected text as a command rather than as content to analyze. If the agent has tools wired up, it may then run shell commands, install packages, or make outbound network requests on the attacker's behalf.

The root cause is structural: agents implicitly trust the logs, MCP responses, and API output they consume. Anything that text touches an LLM context window becomes a potential instruction channel. That is what makes this a class of attack rather than a single bug — and why the fix is defensive architecture, not a one-off patch.

How to resolve

An actionable checklist drawn from current best practice. Treat these as layered defenses — no single item is sufficient on its own.

  • Sandbox your agents strictly. Run AI coding agents inside containers or VMs with least-privilege access, so a hijacked agent cannot reach production credentials, secrets, or the wider network.
  • Treat MCP and API output as zero-trust user content. Logs, MCP responses, and third-party API data are untrusted input — never privileged instructions. Assume any of it may be attacker-controlled.
  • Keep a human in the loop for risky actions. Require explicit human confirmation before the agent installs packages, executes shell commands, or makes outbound network requests.
  • Sanitize and normalize input before it reaches the LLM. Strip ANSI/terminal escape sequences, remove invisible and bidirectional Unicode, and fold homoglyphs so hidden instructions cannot survive into the model's context.

Local-81 Log Guard

We just shipped a security capability in Local-81, an open-source, push-based deploy and runbook control-plane CLI. The capability is called Log Guard, and it applies two complementary controls to logs before an AI agent ever consumes them.

Control 1 · Tamper-evidence

Merkle integrity

At capture time, Log Guard writes a SHA-256-per-file manifest bound under a single RFC 6962 Merkle root. Before any log is consumed, the manifest is re-verified.

  • Proves bytes are unchanged since capture.
  • Detects after-the-fact tampering or substitution.
  • Gives a portable, auditable proof of integrity.

Control 2 · The one that stops injection

Injection scanning + sanitization

Log Guard strips or neutralizes the smuggling vectors attackers rely on, and flags content that reads like an instruction rather than a log line.

  • Strips ANSI / terminal escape sequences.
  • Removes invisible / bidi Unicode and "tag char" smuggling.
  • Flags instruction-override and jailbreak / persona phrasing.
  • Flags role-marker spoofing and tool-call markup.
  • Flags secret-exfiltration, package-install / curl | sh RCE patterns.
  • Flags base64 / obfuscation and link injection.

Honest caveat: a Merkle / integrity check does not, by itself, stop injection. A maliciously crafted log submitted through a legitimate channel is faithfully recorded and will hash perfectly fine — integrity proves the bytes were not altered, not that the bytes are safe. The control that actually defends against Agentjacking is injection scanning + sanitization. Integrity and sanitization solve different problems, and you want both.
